- [x] Real `SearchProvider` — 2026-09-14, **Tavily** (`lib/search/tavily.ts`, `TavilySearchProvider`), prompted by testing the new sourcing feature end-to-end and noticing every generated email said "Hi Jane" (`MockSearchProvider`'s fixed fixture) regardless of which real company was sourced. One search (boosted toward the company's own domain) + one AI extraction call (`decision_maker_search` agent type), same `resultIndex`-grounded anti-fabrication discipline as §11A's sourcing providers, plus an extra code-level guard specifically for email: a candidate's email is only kept if it's verified (in code, not just asserted by the model) to literally appear in that search result's content — never constructed from a name+domain pattern. `tests/unit/tavily-search-provider.test.ts` (6 tests) covers extraction, the email-verification guard (including a test where the model returns a plausible-but-fabricated email and it gets dropped), a zero-results short-circuit, repair-retry on an out-of-range index, and name de-dup. Verified live 2026-09-14: correctly identified Paystack's founders (Shola Akinlade, Ezra Olubi), Flutterwave's CEO (Olugbenga Agboola), and Interswitch's CEO (Mitchell Elegbe) from real pages — no emails found for any of them, which is the honest/correct outcome (none were actually published), not a defect.
- [x] Real, actually-contactable emails — 2026-09-16, **Hunter.io** (`lib/search/hunter.ts`, `HunterSearchProvider`) added as the primary provider, Tavily demoted to fallback (`FallbackSearchProvider` in `lib/search/index.ts`, tries Hunter first, only calls Tavily when Hunter returns zero candidates for a domain). Prompted directly by user feedback: a sourced lead with no way to contact them defeats the point of the whole workflow, and Tavily-only search almost never surfaces a real email since most companies don't publish one in visible text. Hunter's Domain Search API returns already-structured real people per domain (name, position, email, a per-address verification status) from its own licensed data — no AI step at all, so "never fabricate" holds trivially rather than needing a guard. `verification.status` maps to this app's `verified`/`unverified`/`invalid`/`unknown`. Also added `reconcileWithSearchResults` in `agents/decision-maker-agent.ts`: any candidate the outer synthesis call matches back to a real SearchProvider record (by name or source URL) has its email/emailStatus/sourceUrl overwritten from that real record rather than trusted from the model's own transcription — protects a genuinely verified email from being silently corrupted while the model copies it through, which matters now that it actually gets used for sending, not just displayed. `tests/unit/hunter-provider.test.ts` (8 tests: response mapping, all verification-status mappings, a nameless/generic-address fallback, zero-results, non-ok response, and `FallbackSearchProvider`'s primary-wins/fallback-on-empty/error-propagates-not-silently-swallowed behavior) plus 2 new tests in `tests/unit/agents.test.ts` for the reconciliation guard. Verified live end-to-end through the real `getSearchProvider()` factory: 10 real, mostly-verified emails each for Paystack/Flutterwave/Interswitch (e.g. `victoria.adigwe@flutterwave.com`, confidence 0.99, verified). `HUNTER_API_KEY` required for real mode; `SEARCH_API_KEY` (Tavily) becomes optional (fallback-only).
